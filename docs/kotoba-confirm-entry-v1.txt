確認版の入口：案内画面を出さず、表紙へ直接ひらく
====================================================
記録日: 2026-10-07
対象: 確認版（Version 25 以降）の配信方法だけ。アプリ本体のコードは対象外。


1. 起きていたこと
-----------------
確認用のURLを開くと、採用済みの表紙より先に次の画面が出て、
約2秒ほど表示されたあとで表紙へ切り替わっていた（利用者のiPhoneで確認）。

  「確認版 / ことばトラベル / KOTOBA JOURNEY / ひらく」
  「ひらいたあとの短い試しかたです。」
  「りんご・ねこ・いぬの3ペアです。正解すると絵が出ます。学習記録には残りません。」


2. どこから出ていたか（切り分け）
---------------------------------
アプリ本体ではない。
  - リポジトリの index.html と src/ に、この文は1文字も無い。
  - 「りんご・ねこ・いぬ」を含む本体の文言は
    strings.ts の trialLead で、文面が違う（「正解すると絵が出ます。」は無い）。

公開サービス側でもない。
  - 公開物を読み出して確認したところ、サービスが足すのは
    文字コード・画面幅・最低限の体裁だけで、案内文は含まれない。

原因は、こちら側で用意していた確認版の入口ページだった。
  - 公開するとき、アプリのHTMLを app.html という名前の脇のファイルとして置き、
    入口の index.html には案内カードと
    「try { location.replace('app.html'); }」という自動転送だけを書いていた。
  - location.replace は転送を始めるだけで、新しいページが描けるまで
    前のページ（案内カード）が画面に出たままになる。
  - 手元で回線を絞って（下り1.5Mbps・往復150ms）測ると、こうなっていた。
      248ms  入口ページが実際に描画される（first-contentful-paint）＝案内カードが出る
     1073ms  app.html が描画を始める＝案内カードが消え、濃紺の背景だけになる
     1528ms  表紙が出る
    案内カードが画面に出ていた時間は約0.8秒。
    そのあと濃紺の空白が約0.45秒あり、合わせて約1.3秒、表紙でないものが映る。
    実機の回線ではこれが約2秒に見えていた。


3. 直し方
---------
入口ページをやめ、アプリのHTMLそのものを確認版の最初のページとして公開する。
  - ページの読み込みが1回だけになり、途中に映るものが無くなる。
  - 待ち時間を足したり、別の画面で覆ったりはしていない。

  公開の形（Version 25 以降）
    index.html … アプリのHTML（＝これが最初に開かれるページ）
    app.html  … 同じ内容の控え。前のURLを開いても動くように残す
    assets/   … これまでと同じ

今後、確認版を公開しなおすときも、index.html にはアプリのHTMLを置く。
案内カードや自動転送の入口ページを作り直さない。


4. 確かめたこと（手元の実ブラウザ＝Chromium。実機ではない）
-----------------------------------------------------------
回線を絞った同じ条件で、修正前と修正後を測った。

  修正前  ページの読み込み 2回（入口 → app.html）
          入口ページの描画 248ms、app.html の描画 1073ms、表紙 1528ms
          → 案内カードが約0.8秒、そのあと濃紺の空白が約0.45秒
  修正後  ページの読み込み 1回のみ
          最初に描かれたものが表紙そのもの（1392ms）
          → 案内カードは一度も画面に出ない

  初回アクセス・再読み込み・URLを開き直す、の3通りで、
  いずれもページの読み込みは1回だけだった。

サービスが付ける外枠の中にアプリのHTMLが入る形になるが、
表紙の見た目は変わらない。
  - 外枠あり／なしで表紙を撮り比べ、PNGが1バイトも違わないことを確認した。
  - 「旅をはじめる」から人物えらびへ進めることも確認した。
  - 横スクロールなし、JSの例外なし。

なお、外枠の画面幅の指定はサービス側のものになるため、
本体が指定している maximum-scale=1.0 / user-scalable=no は確認版では効かない。
iOS 10 以降の Safari はこの2つをもともと無視するので、iPhone での違いは無い。


5. 2つの確認を分けて記録する
-----------------------------
この工程には、別々に確かめるべきことが2つある。混ぜない。

(ア) 起動時に案内カードが出なくなったこと
     2026-10-08 / Version 25 / iPhone 実機 / 問題なし（ユーザーによる確認）
     確かめた範囲は「案内カードが出ない」ことだけ。
     表紙がどう出るか、どれくらいで出そろうかは、この確認に含まれない。

(イ) 採用済みの表紙イラストが完全に表示されること
     2026-10-07 / 手元の実ブラウザ Chromium / 公開物と同じ入れ子の形 / 確認した
     **実機では未確認。**

     「完全に表示された」の判定は、見た目の印象ではなく、
     表紙で使っている画像を1枚ずつ取り出し、そのすべてが
     読み込み終わって寸法を持っていることで決めた。

       画像3枚（合計 約1.34MB）
         background-walkway-candidate.webp   853x1844   557,066 バイト
         logo.webp                          1997x788    486,754 バイト
         characters.webp                    1024x1536   297,908 バイト
       3枚とも読み込めた。読み込み失敗 0件、JSの例外 0件。

     表紙が出そろうまでの時間は、回線の速さでほぼ決まる。

       回線を絞った再現（下り1.5Mbps・往復150ms）
         1758ms  表紙の骨組み（ボタンなど）が出る
         8485ms  画像3枚が出そろう＝表紙の完全表示
       絞らない場合（手元のサーバー直結）
          100ms  表紙の骨組みが出る
          140ms  画像3枚が出そろう＝表紙の完全表示

     前の比較画像の 1500ms のコマは、骨組みが出た直後で、
     画像がまだ届いていない読み込み途中の状態だった。
     表紙が出ないという不具合ではなく、画像の受信が終わっていないだけ。

     操作の確認
       「旅をはじめる」を押して人物えらびへ進めた。16人が並んだ。
       横スクロールなし。

6. 確認の種類の一覧（この時点）
-------------------------------
  ユーザー実機 … 案内カードが出ないこと        済み・問題なし（2026-10-08）
  ユーザー実機 … 表紙の完全表示                未確認
  手元の Chromium … 案内カードが出ないこと     済み
  手元の Chromium … 表紙の完全表示と操作       済み
  公開された中身の確認（ファイルの読み出し）   済み
  確認URLをブラウザで開いての確認              未実施
  Safari / WebKit での確認                     未確認

追加の起動処理の変更、追加の演出、固定時間の待機は不要との指示を受けている。
表紙の画像が合計 約1.34MB あることは測定結果として記録するが、
軽くする変更は依頼されていないので行わない。


7. していないこと
-----------------
  - 固定時間の待機を足していない。
  - 案内画面を別の画面で覆っていない。
  - 表紙・ボタンのデザイン、学習記録、世界マップは変えていない。
  - アプリ本体のコードは1行も変えていない（この工程の変更は配信方法だけ）。
  - 正式サイト・main への反映は保留のまま。
  - マイパスポートの表示名変更と、「練習中」の保存機能の追加も保留のまま。
    これまでの調査結果はそのまま保持する。
